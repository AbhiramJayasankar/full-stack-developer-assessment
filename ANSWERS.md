# Section 1 — Incident investigation and fix

## Scope and ordered investigation log

Since the assessment does not include an application or deployment history, I built a reproduction around a model-property change. The log below describes how I would investigate the reported incident and which evidence would support that diagnosis.

1. Establish impact first: compare latency by order count, deployment timestamp, status code and tenant. Check DB/worker saturation and error logs before changing anything. A sharp order-count relationship suggests repeated per-row work; a global latency increase would prioritize infrastructure or locks. Preserve the deployment SHA and a safe rollback path.
2. Capture one slow request with Silk in a safe development/staging dataset. Inspect `silk.models.Request` and its recorded SQL queries. Repeated `SELECT ... FROM orders_customer WHERE id = ... LIMIT 21` queries would point to lazy foreign-key loads. Latency alone would not establish an index problem.
3. Compare a small and large dataset, count query shapes and durations, and inspect database plans for dominant queries. Check `QuerySet.explain()` and database connection/query timing. Primary-key lookups already use the PK index, so adding an index cannot remove hundreds of round trips. Check lock waits and connection-pool contention if SQL time does not explain wall time.
4. Diff related model properties, serializers, managers, settings and dependencies as well as the unchanged view. Here `Order.customer_label` changed from using an available ID to reading `self.customer.name`. Django lazily fetches that relation once for each `Order` instance; it has no request-wide identity map, even when orders share the same customer.
5. Reproduce with 250 synthetic orders. Compare identical response JSON and Silk query counts before/after `select_related("customer")`. Run regression tests and inspect the joined SQL. Roll out while observing query count, p95 latency, DB load and response correctness. Roll back if correctness changes.

## Root cause and implementation

Category: **N+1 lazy relation queries introduced by related model behavior**. `broken_summary()` evaluates one order query and then `customer_label` issues one customer query per order. The view itself need not change. The fix in `summary()` adds `QuerySet.select_related("customer")`: Django emits an SQL JOIN and constructs/populates the foreign-key relation cache while hydrating each order. The property then reads the cached customer and emits no additional SQL. `prefetch_related` would use two queries and be appropriate for reverse/many-to-many relations; this single-valued foreign key fits `select_related`.

The Silk capture in `evidence/silk-queries.json` records **251 queries before the fix and 1 after**, for 250 orders. Run `scripts/profile_orders.py` to repeat the measurement. `tests/test_orders.py` checks both query counts and identical response content. Remote database round trips or connection contention could explain the reported 30-second timeout; this local reproduction establishes the query regression, but does not reproduce that exact latency.

# Section 3 — Written architecture review

## Question A — Django Admin Performance

First I would inspect SQL for the change list with representative staff permissions and `list_display`. A column method that reads `obj.customer.name` creates an N+1 query unless the relation is loaded. Set `ModelAdmin.list_select_related = ("customer",)` for foreign keys. For reverse relations, override `ModelAdmin.get_queryset()` with `prefetch_related()` or use `annotate(Count(...))` when the column only needs a count. Avoid calling a new related-manager filter inside each column method: that bypasses a prefetched cache. Verify query count stays constant as the page size increases; a primary-key index cannot remove these round trips.

Second, inspect count and sorting queries. Django's paginator evaluates `COUNT(*)`; the admin can also count the full unfiltered result set. Set `show_full_result_count = False` to remove that extra full-table count, while acknowledging that the paginator still counts filtered results. Reduce `list_per_page`, choose an indexed `ordering`, and create a composite index matching common filters followed by the ordering field. For truly expensive counts, a custom `ModelAdmin.paginator` can expose an estimate or bounded count, but the UI must label approximate totals and may lose arbitrary last-page navigation. Turning off one count is not a complete pagination fix.

Third, inspect search, filters and edit-form widgets. Default text `search_fields` often generates broad `icontains` predicates that a normal B-tree cannot accelerate. Prefer exact/prefix search where the product permits it, or override `get_search_results()` with PostgreSQL full-text/trigram search backed by appropriate indexes. Replace foreign-key dropdowns containing hundreds of thousands of options with `autocomplete_fields` and define indexed search on the related admin, or use `raw_id_fields`. Expensive distinct-value filters deserve removal or a constrained custom `SimpleListFilter`. These changes trade convenience for predictable work; measure SQL and rendering time separately before choosing them.

## Question B — Pagination Trade-offs

Offset pagination maps naturally to numbered pages: `queryset[offset:offset + limit]` becomes SQL `LIMIT/OFFSET`. It is easy to add to an existing API, and DRF's `PageNumberPagination` supports counts and familiar navigation. The cost grows for deep pages because the database still walks and discards preceding matching rows, even with an ordering index. `COUNT(*)` can add another expensive operation. I would choose it for small, relatively static datasets or an admin workflow where jumping to page 40 matters more than perfectly smooth scrolling.

For a mobile infinite-scroll feed, cursor pagination is usually a better fit. Order deterministically by an immutable pair such as `created_at DESC, id DESC`, index those columns with the account filter prefix, and seek using a predicate equivalent to `(created_at, id) < (:timestamp, :id)`. The database can seek into the B-tree and read the next limited batch. A stable unique tie-breaker is essential because timestamps can collide. DRF `CursorPagination` provides cursor mechanics, but its position/offset treatment of nonunique values should be inspected; for a strict composite seek I would implement and test the pair explicitly. Encode the filter/order context and authenticate cursor contents if clients must not modify them.

Concurrent inserts before an offset shift later pages and can repeat records; deletions can cause records to be skipped. A cursor anchored to immutable ordering values avoids that positional drift, but does not create a database snapshot. Updates to filter membership or ordering fields can still change what appears. If users require a consistent export, use a snapshot boundary or materialized export job rather than promising cursor pagination alone provides consistency. Cursor APIs also sacrifice arbitrary page jumps and an inexpensive exact total. I would version or add the pagination contract, cap page size, and preserve a documented migration path for existing clients instead of silently truncating the old 10,000-row response.
